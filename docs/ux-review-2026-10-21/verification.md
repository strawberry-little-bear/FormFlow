# 复核页范围隔离与交互验收记录

更新：2026-10-21。本文记录复核范围与复核页实现的自动化验证和隔离浏览器试走，不代表真实业务库、真实材料或公网部署已经验收。后续已补充工作台下一步建议及 Agent 分工卡的真实浏览器走查截图；Agent harness 自动化测试在下方新进展小节追加。

## 验收目标

本轮围绕三个问题验收：

1. 刷新复核页后，规则理由、资格依据和验收依据是否仍在正确位置。
2. 切换主体、正式版本、登记成员或检查运行后，旧理由是否会被误用。
3. 长复核页是否能让组织者按材料、资格、验收的顺序找到下一步，并在窄屏使用。

## 复核范围不变量

后端为每个复核页面计算不透明的 `review_context`。它包含账号、任务、主体 ID 与身份字段、当前发布蓝图、当前正式修订、最新未取代检查运行，以及按 ID 排序的登记成员 ID、姓名和附加信息。它只用于绑定当前复核范围，不把资格提交状态本身放进范围，避免资格提交后同一范围的未提交理由失效。

公开人工决定请求必须携带页面看到的 `expected_review_context`，并同时携带当前正式修订和资格决定所需的成员哈希。写入前在数据库写锁内重新读取并核对范围。主体、版本、成员或检查运行变化时返回 409，决定不落库；缺少范围时返回 422。前端保留旧范围理由，但新范围不会自动恢复它。

## 2026-10-22 追加：需求 Agent 长调用恢复与提交闭环

### 问题和实现

真实使用中，起草/修订需同步等待模型，客户端或反向代理断开时，用户难以分辨“请求没有送到”还是“服务器已经完成”；重复点击可能再生成一版，刷新后也不确定原文是否还在。优化保持原有“需求 → 草案 → 人工发布”流程，不新加 Agent 工具或外部依赖：

- 新增 `AgentDraftRequest` 持久表。请求写入数据库并返回 HTTP 202 状态/稳定 request ID，再由 API 后台任务尝试执行；既有单 Worker 同样轮询处理持久队列。
- 请求按任务串行，幂等 ID 绑定请求内容 hash；同 ID/同输入查询或恢复既有结果，不重复创建版本；同 ID/不同输入拒绝。
- 编辑器在现有 owner/task sessionStorage 暂存原文、回答和请求 ID。队列/处理中期间显示人能理解的状态；网断、刷新后先查状态，若原请求尚未入列，再以相同 ID 补送。客户端用 no-store 查询状态，防止中间缓存回放旧状态。
- 只有完整模型响应才保存为草案；模型超时、连接断开或 JSON 不可解析时不创建空版本，显示失败/同请求重试。多个标签页竞争时以提交前最新 blueprint ID 校验，避免迟到响应覆盖新草案；Worker stale lease 依据当前模型超时/重试设置宽裕计算，并使用 attempt fence 忽略超期旧 Worker 的迟到提交。
- 队列不是分布式通用任务系统；当前定位为现有本地 SQLite/WAL + 单 API/Worker 原型，运行时每个任务只串行处理一个待做请求。多副本上线前仍需跨数据库的租约/锁、死信、退避和监控设计。

## 2026-10-22 追加：附件上传/删除纳入草稿并发版本

### 发现与改进

提交者可能在手机和电脑、或两个浏览器标签页同时填写。此前附件上传只追加文件清单、不递增 `draft_version`；另一标签页基于旧版本保存完整附件清单时，CAS 仍会通过并覆盖刚上传的附件引用。文件本身不会被物理删除，但草稿看不到它，槽位数量也可能继续被占用。

- 上传与删除现作为正式草稿变更：请求携带 `expected_version`，服务端先核对数据库当前版本，再用原子 CAS 推进版本并基于最新服务端清单追加/删除目标文件；不会用旧页面的整张清单覆盖附件状态。
- 上传/删除成功返回新的 `draft_version`；前端同步该版本并将文件操作反映到服务器基线。后续保存只会覆盖基于正确版本的内容；如果期间字段仍有未保存修改，仍显示为本地暂存，而非错误标为已同步。
- 过期标签页的上传/删除返回 409，文件选择与本地填写保留，用户可查看冲突提示后明确使用“重新加载服务器草稿”；正常场景无需额外点击“保存草稿”才能让附件引用留在服务器。
- 后端新增回归验证：上传后旧标签完整草稿保存被拒且新附件留存；旧版本重复上传与删除被拒，当前版本删除成功并递增版本。Node VM 契约验证上传/删除都提交基准版本并接收服务端新版本。
- 原件删除改为数据库事务提交后执行；若草稿数据库写入回滚，磁盘原件仍保留。提交成功后清理失败会记录服务端警告并向提交者明确提示，避免把“已从草稿移除”误报为文件已清理。

## 2026-10-22 追加：交付导出完整性保护

### 发现与改进

审查组织者固定快照后的真实交付路径发现，ZIP 导出过去会对缺失的 `FileObject` 或原件执行 `continue`，最后仍将作业标记为成功；组织者可能收到与快照不一致的包。

- 创建快照时遇到正式版本引用但数据库中已不存在的文件记录，立即拒绝固定快照并指出文件 ID，不把缺失材料静默抹掉。
- 导出前核对所有纳入材料对应记录和原件；写入 ZIP 时流式校验实际字节数与固定快照中的大小、SHA-256。丢失、读取失败或被改写时作业记录为 `failed`、清空下载路径，并清理本次临时产物。
- CSV/ZIP 使用作业唯一的临时文件，完整成功后才原子改名为可下载文件；API 不为失败作业提供下载，历史成功文件若后来丢失则返回 410。交付页失败时显示错误但不提供下载按钮，组织者可恢复存储后重新生成。
- 回归覆盖快照缺失记录、原件缺失、内容被改写、失败作业下载拒绝、已丢失导出文件提示，以及前端无下载入口。完整套件最终 **335 项 Python、84 项 Node 前端契约通过**。
