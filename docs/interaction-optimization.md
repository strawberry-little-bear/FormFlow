# 交互契约修复与后续优化

更新：2026-10-20。依据 `docs/收齐啦产品设计方案_v0.3.docx` 及其提取文本；基于主线 `739b7ec`，保留该主线的新布局、发布校验与草稿恢复能力。

## 本轮已实现

### 1. 截止时间是一条时间线，不是两套本地时间
- 蓝图中的无偏移时间按任务的 IANA 时区解释，持久化统一为 UTC。
- API 明确输出 UTC 偏移；设计台与提交页按任务时区展示，避免 SQLite 返回无时区时间造成 8 小时偏差。
- 发布时同步任务时间策略，服务端截止判断与页面显示使用同一时刻。

### 2. 应交、正式提交、检查、验收分层
- 名册任务：应交 = 名册人数 - 有效免交人数；未发凭证的名册成员仍计入应交。
- 免交者即便上传或正式提交，也不回到应交、未提交分母。
- 开放任务没有预设应交分母，不展示虚假的完成率。
- `special_deadline` 不是免交；工作台与催交名单共享免交筛选。
- 正式版本独立于检查运行：尚无检查结果时，仍显示其真实版本。

### 3. 本地暂存、服务器草稿、正式版本明确分开
- 字段、附件引用与附件名称按任务和主体隔离；逐步填写中未点“下一题”的输入也暂存。
- 本标签页刷新/切页恢复依靠 sessionStorage；存储不可用时使用内存兜底，并提示刷新风险。
- 点击保存草稿才写服务器；使用 `expected_version` 比较并交换，冲突返回 409，不静默覆盖任一方。
- 本地与服务器内容相同时采用服务器最新版本号，不因陈旧缓存制造假冲突。
- 保存期间继续输入不误报“全部已保存”；上传、保存、提交的晚响应不能写入另一个主体的页面。
- 同内容正式提交失败重试复用幂等键，防双击；成功后下一轮修改使用新键。
- 正式回执和历史版本不被草稿修改；显式清空草稿不复活旧正式字段。
- 重新加载服务器草稿是显式替换操作，需确认；目前不提供自动三方合并或跨设备未保存输入同步。

### 4. 人工决定绑定实际看过的版本
- 决定请求必须携带 `expected_current_revision`，值是数据库 Revision ID，不是页面的 v1/v2 序号；0 表示尚无正式版本。
- 写入决定前锁定写入并重新读取当前版本。看过 v1 后主体补交 v2，旧请求返回 409，不能落到 v2。
- 页面保留理由和旧证据、禁用旧页继续提交，提供明确的刷新核对入口。
- 验收检查不借用旧版本或已失效的决定。

## 验证

```sh
python -m pytest -q
node --test tests/frontend_contracts.test.cjs
node --check app/static/app.js
git diff --check
```

本轮结果：232 项 Python 测试、13 项前端契约测试通过。前端测试使用 Node VM 和 Mock DOM/fetch，不是浏览器端到端套件。现有 SQLAlchemy 外键环、datetime 与 TestClient 依赖弃用警告仍在，不等于已完成上线验证。

隔离 SQLite 测试库的浏览器试走已验证：未点下一题的字段切页恢复、服务器草稿恢复、双标签保存冲突保留本地输入、旧版本复核拒绝。提交页另检查了 390px 窄屏与主要操作，无横向溢出。未对真实业务库或真实材料进行操作；没有覆盖所有页面的移动端验收。

## 协作和提交约定

- 每轮开始与提交前 fetch 主线，检查是否有重叠变更；只有安全快进或明确整合后才继续，不覆盖别人的未提交修改。
- 数据契约、界面调整、文档分批提交并推送 `codex/interaction-contracts`；已推送提交不重写。
- 提交报告区分自动化测试、浏览器人工试走、尚未实现的计划；不将测试通过描述成生产可用。
