# 交互契约修复与后续优化

更新：2026-10-24。本文记录 `main` 上的交互契约与迭代结果，依据 `docs/收齐啦产品设计方案_v0.3.docx` 及其提取文本。历史段落保留各自基线和测试数字；最新工作台、Agent 运行轨迹、需求长请求恢复、附件并发保护、交付历史恢复与任务首页展示视图见文末，当前验证为 340 项 Python / 97 项 Node 前端契约通过。历史 `e158340` 描述不再代表当前 `main` 最新提交。

## 本轮已实现

### 1. 截止时间是一条时间线，不是两套本地时间
- 蓝图中的无偏移时间按任务的 IANA 时区解释，持久化统一为 UTC。
- API 明确输出 UTC 偏移；设计台与提交页按任务时区展示，避免 SQLite 返回无时区时间造成 8 小时偏差。
- 发布时同步任务时间策略，服务端截止判断与页面显示使用同一时刻。

### 2. 应交、正式提交、检查、验收分层
- 名册任务：应交 = 名册人数 - 有效免交人数；未发凭证的名册成员仍计入应交。
- 免交者即便上传或正式提交，也不回到应交、未提交分母。
- 开放任务没有预设应交分母，不展示虚假的完成率。
- `special_deadline` 不是免交；工作台与催交名单共享免交筛选。
- 正式版本独立于检查运行：尚无检查结果时，仍显示其真实版本。

### 3. 本地暂存、服务器草稿、正式版本明确分开
- 字段、附件引用与附件名称按任务和主体隔离；逐步填写中未点“下一题”的输入也暂存。
- 本标签页刷新/切页恢复依靠 sessionStorage；存储不可用时使用内存兜底，并提示刷新风险。
- 点击保存草稿才写服务器；使用 `expected_version` 比较并交换，冲突返回 409，不静默覆盖任一方。
- 本地与服务器内容相同时采用服务器最新版本号，不因陈旧缓存制造假冲突。
- 保存期间继续输入不误报“全部已保存”；上传、保存、提交的晚响应不能写入另一个主体的页面。
- 同内容正式提交失败重试复用幂等键，防双击；成功后下一轮修改使用新键。
- 正式回执和历史版本不被草稿修改；显式清空草稿不复活旧正式字段。
- 重新加载服务器草稿是显式替换操作，需确认；目前不提供自动三方合并或跨设备未保存输入同步。

### 4. 人工决定绑定实际看过的版本
- 决定请求必须携带 `expected_current_revision`，值是数据库 Revision ID，不是页面的 v1/v2 序号；0 表示尚无正式版本。
- 写入决定前锁定写入并重新读取当前版本。看过 v1 后主体补交 v2，旧请求返回 409，不能落到 v2。
- 页面保留理由和旧证据、禁用旧页继续提交，提供明确的刷新核对入口。
- 验收检查不借用旧版本或已失效的决定。

### 5. 复核操作与整体验收拆开
- 人工核对项取自检查运行绑定的蓝图，不伪造机器 RuleResult；原有机器结论与证据仍与提交者端同源。
- 待核对项优先，人工决定以单独叠层显示，不覆写原始检查结论；历史区区分本版本、历史修订与名单级决定。
- 验收作为独立操作，显示现有服务端验收门槛的阻塞原因，使用单独理由且不继承规则作用域或过期时间。
- 未提交的规则理由、资格依据和验收依据按任务 / 主体 / 正式修订 / 登记成员 / 检查运行组成的不透明复核范围，分别保存到当前标签页的 `sessionStorage`；切规则、切页和刷新可恢复，关闭标签页不保证保留，页面显式提示。
- 决定提交期间锁定当前复核控件，晚响应不能清空其他规则的理由或返回另一主体的旧复核页；版本冲突同时锁定决定和验收。
- 撤销的反向记录只作为历史，不再算作当前规则的有效处置。免交撤销与 Exemption 已在本轮建立关联。

### 6. 提交与身份切换更聚焦
- 提交页默认完整表单，逐步填写为辅助；引导结束区不再重复放置保存 / 正式提交按钮，上传与引导本身仍保留。
- 双身份并存时以当前页面显示组织者 / 提交者角色，明确提供身份切换入口；复核页沿用工作台导航高亮。
- 结果仅在排队 / 运行 / 重试待定时自动轮询；解释输入及光标保留，失败显示局部重试入口，晚响应不覆盖新页面。

### 7. 工作台刷新不打断编辑
- 自动刷新保留催交文案（含主动清空的文案）、勾选目标与文本焦点；已不符合催交条件的目标被移除，不自动重新勾选其他人。
- 六张名册统计卡桌面三列、窄屏两列，复核规则标题优先于技术 ID，移动端仍使用局部横向规则列表而非整页溢出。

### 9. 工作台主动给出“下一步”，仍把决定留给人

- 根据服务端现有状态，优先指向待补正、资格待核、待人工、检查未完成、运行中或待验收主体；有阻塞时优先于其他人。
- 如果当前没有正式版本待办，提示未正式提交名单；当主体都已验收或有效免交时，提供交付清单入口。每种状态都使用不同解释，不把草稿当正式件、不把技术失败当业务不合格，也不催免交者。
- 卡片说明“为什么推荐这一步”和状态的边界；主操作只导航到复核、筛选名单或交付页，不替组织者决定、批准资格或确认验收。完整列表始终保留。
- 桌面显示轻量行动卡；窄屏改为纵向布局。排序逻辑确定性、可单测，不用模型推断人员优先级。

### 10. 复核页解释 Agent / 工具分工，不伪装已有 MCP

- 在复核工作流中增加可收起的执行说明：材料提取 → 确定性程序规则 → 按需语义审核 → 人工决定/资格/验收，分别展示当前运行状态、规则项数量、页面读取和语义预算。
- 告知组织者：模型只按已确认规则找原文依据；证据不完整会停在待确认；程序校验、模型意见和人工决定独立保留。
- 当前已增加审核专用 skill 与内部工具 harness；它不是可供模型自由规划的通用 registry，也不是 MCP Server/Client。页面说明只展示真实的程序/语义/人工分工，不显示虚构 MCP 调用轨迹。核心不变量和单测范围见 [`docs/product-roadmap.md`](product-roadmap.md)。

### 11. 正式提交完整性与缺项定位
- 服务端在生成正式版本、回执、草稿更新及检查任务之前，使用当前发布蓝图校验必填字段、枚举选项、条件必交材料、数量、文件归属及格式 / 大小；数值 0 不视为空。条件与后续检查共用判断器，不支持的条件显式要求联系组织者。
- 不完整内容仍可保存草稿；正式提交失败返回结构化 422 错误（字段 / 槽位 ID、错误码、文案），不生成假回执，也不修改旧正式版本。旧版不完整快照仍可检查，保留兼容性回归覆盖。
- 页面聚合缺项并自动展开完整表单；摘要按钮可定位到字段 / 附件输入，错误通过 `aria-describedby` 与 `aria-invalid` 关联。逐步填写中未点“下一题”的输入及已有附件引用均保留；晚响应不能污染其他主体页面。
- 填写 / 上传计数随页面草稿更新，空白不计数、0 计数；清空字段后重新进入向导会回到待填题，不再静默跳过。
- 同键同内容顺序重试复用原回执和已有检查运行，不再重复排队；任务关闭后仍能恢复已成功的回执。本轮未增加并发请求的数据库唯一约束。
- 这是结构性收件校验，不代替材料语义、实际文件类型或页数检查，也未覆盖所有字段类型校验。

## 协作和提交约定

- 每轮开始与提交前 fetch 主线，检查是否有重叠变更；只有安全快进或明确整合后才继续，不覆盖别人的未提交修改。
- 按用户最新要求，仅在 `main` 上开发和推送；不再创建功能分支。已推送提交不重写。
- 提交报告区分自动化测试、浏览器人工试走、尚未实现的计划；不将测试通过描述成生产可用。

### 2026-10-20 免交生命周期与名单入口

- 远端重写过历史；本轮先核对 `origin/main` 的 `288db64` 文件状态，再将仅有的两笔增量提交应用到原有 `codex/interaction-contracts`。按用户要求删除临时创建、尚未推送且无独有提交的 `codex/exemption-lifecycle`；不创建替代分支，不强推重写远端历史。
- 新免交通过 `Exemption.decision_id` 关联人工决定，对整个任务生效。撤销只失效该条免交；有其他有效免交时仍保留免交。到期判断使用 UTC，并在恰等于截止时失效。已有正式版本、回执和历史决定保留。
- 名册、工作台、催交、新快照共用有效免交查询。正式快照排除有效免交者并说明原因；撤销或到期后的新快照重新判断纳入条件，仍需当前版本已验收。旧快照及旧通知目标不回写。
- SQLite 启动升级仅补充可空关联列。旧记录只在任务、主体 ID、理由、操作者一致，创建时间相差小于 2 秒且双方唯一时关联；独立名单例外及有歧义旧记录保留原状。**未覆盖历史数据的人工核对流程**；不能声称所有手工编辑过的旧库均已完成免交迁移。
- 决定过期时间不带偏移时按任务时区解释，已过期时间拒绝保存；撤销接口校验路径中的主体归属。撤销记录不可再次撤销。
- 统计卡改为键盘可操作的筛选按钮。点击统计时清空搜索，名册模式下已提交/未提交/验收筛选与分母一致；免交但已提交者不会混入应交。尚未提交者新增“处理免交 / 免交与历史”入口。
- 撤销改为页面内弹窗：展示影响、要求理由、防重复提交、失败保留理由。浏览器试走发现并修复原生 prompt 在内嵌浏览器无法输入的问题，也修正无正式版本时的检查提示。

### 2026-10-20 规则决定与验收效力

- 修复“确认问题”曾被视作解除阻塞的缺陷。新增 `confirm_pass`（人工核对通过）；`confirm_issue` 保留补正待办，`confirm_pass` / 纠正误报 / 批准例外只解除当前规则。同一规则按最新有效决定计算，原始 RuleResult 和证据不改写。
- 规则决定必须指定当前正式版本及其检查蓝图中的真实规则，未绑定修订的历史规则决定不能扩展到后续版本。过期、撤销记录不作为当前处置。
- 验收读取同一份实时阻塞条件；后续规则决定、规则决定撤销或重新检查会使旧验收失效，解决问题后仍需单独重新验收。撤销最新验收不复活更早的验收。新正式快照跟随有效验收，旧快照保留原清单。
- 人工前提若要求资格符合，`ineligible` 同样阻止验收，不能只拦待核资格。**本轮没有补齐资格决定本身撤销/到期后的结论重算**，列入下一轮 P0。
- 复核页默认要求明确选择结论，“确认问题”仍计入问题数并优先展示；历史验收失效时标注“当前不生效”。提交者和组织者共享规则明细及独立的人工决定叠层；人工待核项不伪造机器结果，旧检查建议明确标为“原始检查建议”。
- 申诉只有在同一修订、同一规则存在提交解释之后的有效决定时才标为已处理，决定到期/撤销后恢复待处理。
- 更新演示种子中原本借用“确认问题”表示“核对通过”的写法；不自动改写已有业务决定的理由或类型。旧库中以 confirm_issue 错记通过的记录需要组织者重新核对并记录明确结论，不能靠猜理由自动放行。

### 2026-10-20 独立资格复核闭环

- 资格决定保存明确结论（符合 / 不符合 / 待核实）、理由、有效期、正式版本、登记成员范围及操作者。API 接收资格结论，并同时验证页面看到的正式版本和成员范围；成员变化返回 409，保留输入并要求刷新核对。

### 2026-10-20 设计台输入恢复与发布核对

- 生成的服务器草案、尚未发送的需求、澄清答案和额外意见明确区分。输入按已认证账号、任务、起点草案 ID 放入 sessionStorage，内存作降级；切页及刷新恢复仅限本标签页，关闭标签页后不承诺恢复，不提供跨设备同步。
- 当前草案与缓存起点一致时恢复原输入；草案已变更时保留旧内容，显式“复制为当前修改意见”，不把旧问题答案自动应用到新版本。页面渲染对话不会清空未完成答案。只消费这次真正发送的内容：发送需求不清澄清答案，提交澄清不清另一段未发送需求。

- 发布弹窗先刷新设计状态，按当前已发布蓝图展示累计变化（字段/材料/规则增删改、时间、资格、验收及配置变化提示），然后核对完整要求；焦点停在顶部差异说明。初次发布显示“首次发布”。
- 公开发布接口必须携带已核对的发布基线；写入前锁定并重读当前发布指针。基线或最新草案变化返回 409，过期核对窗口不能继续提交；历史已发布蓝图不能回滚当前版本。内部服务保留可选基线参数供受控调用使用，公开 API 不可省略。已发布当前版本重复调用不重复写发布记录。

### 2026-10-21 复核页范围隔离与可恢复理由

- 后端新增 `review_context`：由账号、任务、主体身份、当前发布蓝图、正式修订、最新未取代检查运行和有序登记成员共同计算 SHA-256 不透明范围。理由和决定请求都必须绑定这个范围。资格结论本身不改变范围，避免提交资格后同一页面的未提交材料理由突然失效。

### 2026-10-22 需求长请求恢复与完整合成流程

- 结合组织者流程发现最现实的薄弱点：设计 Agent 请求原先同步等待模型；浏览器或代理断开时，组织者难判断是否已完成，刷新后也不清楚能否安全重试。
- 新增 `AgentDraftRequest` 持久队列与状态端点。UI 发送前将请求 ID、原始输入和版本基线写入现有按 owner/task 隔离的 sessionStorage；状态区显示等待/处理中/恢复中/失败。API 202 返回后可轮询，刷新时先按原 ID 查状态；只有确实不存在才用同 ID 同 payload 幂等补送。完成后重新读取当前设计，再决定展示结果。
- 同一 task 由 API BackgroundTasks 与已有单 Worker 共用队列；每 task 顺序串行、同 request ID 用 hash 确保 payload 一致，过期 running 按动态模型重试上限 recovery lease 重新排队；attempt fence 阻止迟到 Worker 提交。不同版本基线冲突时不覆盖并要求显式刷新。模型失败不保存空草案；保留原文与服务器草案，重试沿用原 request ID，避免多建版本。
- 新增 6 个队列回归（请求完成重放、请求中途失败/原 ID 重试、同 ID 不同内容、跨账号状态隔离、旧版本冲突、stale lease recovery）；Node 前端新增刷新后只 lookup、请求响应丢失后 lookup 再补投、请求中/错误分状态和输入保留等契约。
- 全隔离流程用合成材料在浏览器与本地服务走查：设计请求在无 Key 演示模式下正确失败且不建空蓝图，刷新后原文与请求状态还在；组织者工作台/李四轨迹可浏览；赵六合成 TXT 正式提交生成回执 `R6F62AC219DAE1260`，确定性项完成、语义项无模型时失败转人工；组织者逐条人工核对、单独验收，然后快照 #2 正式纳入张三与赵六，排除未验收李四/王五及免交孙七；导出 job #1 的 CSV/ZIP 均返回 200。

- 1440px/390px 工作台、提交者和 Agent 恢复页浏览器检查，390px 无横向溢出、console/errors 为空。需求长请求恢复和全链路截图见 [验收记录](ux-review-2026-10-21/verification.md)。最新全量 335 Python/84 Node 通过；无密钥队列流程不意味着模型起草成功，本次刻意验证的是原文、队列和草案在失败时不丢不重。
- 真实使用风险检查还发现，旧标签页可能在另一页上传附件后，用旧版本清单保存而覆盖新增附件。现在上传与删除均执行草稿版本 CAS 并返回新版本；旧标签页保存、上传或删除会收到 409，不会改写其他页面的附件清单。前端继续保留本地填写和选中的文件，组织者/提交者可选择重新加载服务器草稿再继续。新增 API 回归覆盖上传后旧保存拒绝、旧上传拒绝、旧删除拒绝及最新版本删除成功；前端契约验证上传/删除传递和更新版本。文件原件现在在数据库提交成功后才清理；数据库事务回滚时保留原件，提交后清理失败则返回可见提示并记录服务端警告。
