# FormFlow 交互设计说明

这份文档说明 FormFlow 的页面结构、状态语言和关键交互原则。它面向产品维护者和设计评审，不是按日期记录的开发日志；历史走查请看[走查证据索引](ux-review-index.md)。

## 信息架构

组织者侧按工作顺序组织为：任务列表、需求设计、名单与凭证、收集工作台、证据复核、交付与归档。提交者侧围绕一个任务展开：身份、字段、材料、草稿、正式提交、核对进度和更正。

页面之间共享任务、提交者和版本上下文。标题、面包屑、返回入口和空态都应让用户知道自己正在处理哪个任务和哪一版提交。

## 状态语言

FormFlow 把“材料状态”和“处理状态”分开表达：

- 上传表示文件已收到；保存草稿表示内容已暂存；正式提交才产生可审核版本。
- `satisfied` 表示已有证据支持规则；`issue` 表示发现需要处理的问题；`unknown` 表示证据不足；`failed` 表示检查过程未完成。
- “需要提交者处理”和“需要组织者确认”使用不同区域和动作，避免把等待人工决定误导成提交者的待办。
- 过期、免交、未提交、未验收和已归档分别显示，不能合并成一个总状态。

## 需求设计台

设计台先展示来源和解析状态，再展示 Agent 草案。每条字段、材料槽位和规则都可以追溯到来源；冲突和缺失信息先以澄清问题呈现。发布动作需要组织者明确确认，草案生成失败时保留原输入和可恢复状态。

来源资料支持文本和文件两种入口。文件直传、文字解析和 OCR 降级路径要在界面中如实显示，不能把“已上传”写成“已理解”。

## 收集与提交

提交者看到的是一条连续流程：填写身份和字段、上传材料、保存草稿、正式提交、查看回执、处理更正。缺项应定位到具体字段或材料槽位；条件材料说明适用条件；上传失败和服务器草稿恢复都应给出下一步。

组织者工作台优先展示需要行动的人：未提交、需要补正、需要人工确认和已过截止但仍可处理的主体。催交范围必须说明排除免交、已提交和不再适用的主体。

## 审核与证据

复核页按规则列出结论、解释、来源文件和页码/位置。证据是模型给出的定位线索，程序会检查文件 ID、位置格式和引用非空，但仍允许组织者打开原文核对。证据不足时显示人工接管入口，而不是猜测结论。

## 响应式与可访问性

核心路径需要在桌面、390px 和 320px 下保持可操作：不出现整页横向滚动，主要操作不被固定底栏遮挡，长文件名和长任务名自然换行。键盘路径应覆盖登录、设计、名单、工作台、复核、交付和提交者表单；状态变化使用可感知但不过度打断的播报。

## 设计取舍

FormFlow 是工作工具，不是营销落地页。页面优先展示当前任务、待处理事项、证据和下一步动作；装饰性内容让位于信息层级。模型能力必须与确定性程序检查、权限控制和人工决定并列呈现，用户不能只看到一个无法解释的“AI 结论”。
