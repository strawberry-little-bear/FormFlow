## 一、会真的挡住人的问题

### 1. 一键启动脚本的 `--port` 参数失效（最该先修）

```
$ python scripts/start_demo.py --reset --port 8011
端口 127.0.0.1:8011 已被占用；未修改演示数据。
```

8011 没有任何进程监听（`netstat` 无记录，curl 直连失败）。真实原因是 8000 被我另一个实例占着，而脚本检查的是 8000，却把 8011 打印出来。

根因：`scripts/start_demo.py:119` 的 `def port_available(port: int = API_PORT)`，默认值在**函数定义时**求值，固定成了 8000；`main()` 里 423 行才 `global API_PORT = args.port`，之后 443/449 行调用的仍是无参 `port_available()`。

后果：只要 8000 被占用，任何 `--port` 都失败；反过来 8000 空闲时，脚本会"检查 8000、启动 8011"。报错文案还指向错误端口，排查方向直接被带偏。修法是一行：调用处显式传 `API_PORT`。

顺带一条：`--reset` 会先 `stop_demo()`，输出了"已停止登记的演示进程：api, worker"，但那两个 PID 早已退出，属于误报。

### 2. 「名单与凭证」「证据复核」在无效 ID 下永久卡在加载态

| 地址 | 表现 |
|---|---|
| `#/workbench/9999` | ✅ "暂时无法连接服务端，任务不存在或无权访问" + 重试 |
| `#/delivery/9999` | ✅ "任务不存在或无权访问" + 重试 |
| `#/roster/9999` | ❌ 永远"正在读取名册…"，**没有任何错误提示** |
| `#/review/1/9999` | ❌ 红色"主体不存在或不属于该任务"和"正在读取检查结果…"同时存在 |

两个页面接口都返回 404，是前端没接住。

- 复核页：`app/static/app.js:3144` 把占位 `<div id="rv">正在读取检查结果…</div>` 写进 DOM，`:3169` 的 `catch` 只调了 `setFlash(e.message)` 就 `return false`，从没替换 `#rv`。所以错误横幅和"加载中"会一直并存，用户不知道到底该等还是该退。
- 名单页更糟：连横幅都没有，且左侧"导入名册"面板完全可交互——可以粘贴名单、点"导入名册"，对着一个不存在的任务提交。

workbench / delivery 已经做对了，说明这不是设计取舍，是这两页漏了失败态。截图：`roster-9999.png`、`review-9999-after5s.png`。

## 二、让人犯迷糊的地方

### 3. 「我的任务」页找不到我的任务

点"体验演示环境"进来，`body` 直接带上 `presentation-mode`，`.task-section`（真正的任务列表）被 `display:none` 隐藏，首屏是 1958px 高的展厅（DEMO ROUTE / FIRST LOOK / AGENT CONTROL PLANE / LIVE SHOWCASE STATE / RUN STAGES / RUN EVIDENCE PULSE …）。

点右上角"退出展示视图"回到普通视图后，页面 **2761px** 高，而账号里只有 **1 个任务**——它排在页面最底部，要滚约 2.5 屏。中间隔着 12 个区块的说明性内容。

演示语境下这套展厅是自洽的，但对"点进来看看这是什么"的人，第一眼看到的是产品介绍页而不是产品。截图：`tasks-normal-1440.png`。

### 4. 提交者页把"只有组织者能做的事"算进"需要你处理"

赵六正式提交后，材料进度卡片：

```
需要你处理的内容会放在前面
当前进度：有几项需要组织者确认 · 第 1 版
组织者核对 1 项   检查未完成 2 项
需要一起处理（3）
```

这 3 项分别是"组织者终验报告质量"和两条"检查未完成（未配置模型密钥）"。提交者对它们**做不了任何操作**，卡片自己也写着"需要组织者确认"。上一行说"组织者确认"，下一行说"需要你处理"，同一张卡里两种口径。真实后果是提交者坐在那儿等一个不会来的结果。

截图：`submitter-progress-zoom.png`。

### 5. 320px 下"重新加载服务器草稿"被折断

```
重新加载服务器草 / 稿
```

和右边"保存草稿"高度不齐。390px 下三个次要按钮高度 34 / 31 / 43px 也不一致。主操作"提交材料并开始核对"在 390px 时仍在首屏之外，要往下滚才看得到。截图：`submitter-actions-320.png`、`submitter-actions-390.png`。

### 6. 交付页一个屏里两个"生成 CSV + ZIP"

历史快照行一个、快照详情卡底部一个，都是主按钮样式，点哪个都一样。另外已有快照后"固定快照"仍是无提示的主按钮，再点会生成 #2，而旁边写着"快照固定后不可追加"——两句放在一起容易读成"不能再来一次"。

### 7. 复核页同屏两个统计口径

顶部四宫格 `6 满足`，下面运行摘要写 `已满足 5 / 人工项 1`。数字没错（人工项已由人核对通过，计入满足），但两个口径并排出现，第一眼像对不上。

## 四、这轮确认变好的部分

- **启动脚本的编码问题已修**：`tasklist` 改用 `encoding="mbcs"`，`--check` 在中文 Windows + `PYTHONUTF8=1` 下正常输出，不再 traceback。
- **导出 ZIP 时间戳已修**：条目是 `2026-10-26 21:57:34`（上一轮是 1980-01-01），中文文件名 UTF-8 标志位已设。CSV 里 `2026-10-26 21:57` 是任务时区的本地时间，能直接读。
- **没配模型密钥时的降级文案**：`这次检查没能完成，材料已经收到；这不代表不合格。` —— 把"没检查"和"不合格"分开，这是这条产品线最值钱的一句话。
- **快照排除原因**：`有效免交（不等于材料验收）`、`当前版本未验收`，并且明确告知"有 4 个主体未纳入……可在工作台逐个人工验收后重新固定"。
- 提交者 8 步全流程（凭证登录 → 填写 → 上传 → 存草稿 → 刷新恢复 → 引导跳过已传材料 → 正式提交 → 回执）一次跑通，**零控制台报错**。
- 390 / 320 无横向溢出；正常路径没有 404/500，只有手动输入无效 ID 时才有预期内的 404。

## 五、如果只修三件

1. `port_available()` 显式传端口 —— 一行，挡住的是"第一次启动就失败"。
2. 名单页 / 复核页补失败态 —— 把 `#rv` 和"正在读取名册…"的占位在 catch 里换成错误 + 返回工作台。
3. 提交者材料进度卡片区分"你要做"和"组织者要做" —— 现在这句话在骗人。
