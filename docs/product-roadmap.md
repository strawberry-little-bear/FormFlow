# 从可演示原型到适合人用的 FormFlow

更新：2026-10-24。依据产品方案 v0.3；这是后续设计与验收路线，不代表所有条目已经实现。

## 产品主张与不做什么

围绕一个收集任务提供完整闭环：要求 → 收件 → 有证据的补正 → 人工验收 → 正确版本交付。先验证团课材料场景，再验证团队比赛报名的复用性。不扩展成通用流程引擎，不做文章打分、真实性认定或 AI 写作检测。

判断一次迭代是否值得做：**它是否减少一次找入口、猜状态、重复填写或拿错版本？** 不以多一个聊天窗口或多一张统计图作为完成标准。

## 当前已落地

- 五个工作区贯通：需求设计、名单与凭证、收集工作台、证据复核、交付与归档；提交者有独立填写/回执/结果入口。
- 设计输入恢复、发布差异与基线冲突保护；提交缺项定位、草稿并发保护、不可变正式版本；规则证据、申诉、人工决定、独立资格与免交生命周期；固定快照 CSV/ZIP。
- 本轮补齐：三类复核理由刷新恢复、账号/主体/版本/成员/运行隔离、后端复核范围前置校验、晚响应不清新输入、材料/资格/验收导航、下一待处理与“只看待处理”规则筛选；工作台增加按补正/资格/人工/技术状态排序的下一步建议，复核页可展开“程序检查 → 按需语义审核 → 人工接手”执行说明。
- 下一步建议仅用服务端已有状态生成导航，不代表 AI 决定，也不改写任何规则或人工状态；建议优先级是确定性 UI 逻辑，用户始终可以查看完整名单和自行判断。
- 工作台下一步建议及复核 Agent 分工卡已通过 1440px / 390px 隔离演示浏览器走查；提交者核对卡又一轮桌面/手机走查，390px 页面均未横向溢出。截图和检查条件见 2026-10-21 验收记录。
- 提交者状态卡将 rule_id、网关错误和“模型没引用到”转为下一步可懂的说明；unknown 表示暂时无法确认，failed 表示检查没完成，满足项不再衍生补件建议。Agent 提示已明确限制在当前规则，语义满足时不建议额外材料。
- 用户提供的网关对一条合成语义规则成功返回结论，并通过原文引用验证；长请求需求起草仍出现超时/上游断开，草案被安全保留。单个成功例不证明模型准确率；真实用户收益和模型质量仍未评估。演示种子依旧是脚本桩。
- 需求设计台新增“发布前核对”一页汇总：提交对象、字段与材料、双截止、规则分工、最终验收、交付方式及数据边界集中呈现，并沿用服务端阻塞项与提醒状态；同时把需求 Agent、复核 skill、harness 与 MCP 边界显示在页面上。无模型密钥时明确进入“离线可演示”状态，模板和手动编辑仍可用。
- 版本差异已进入设计台日常视图：最新草案与历史只读版本都会显示相对当前已发布版本的字段、材料、规则、时间、资格、验收、交付与治理变化；历史接口同时返回发布基线，发布确认继续复用同一套差异描述，避免只在最后一步才发现范围变化。

### 真实试走脚本（先虚构或授权脱敏材料）

招募组织者与提交者分别完成：建立任务并解释要求、收到邀请后提交、读懂补正并更新、人工判断与验收、下载正确交付包。记录每个卡点、误点、打开原文件次数、处理时长及机器意见被纠正的原因，不预设“节约多少”。失败也必须记录。

## Agent 工具运行时：可信内核已起步，MCP 暂不需要

**已落地最小内部运行时**：`app/agent_tools.py` 定义严格输入/输出 Schema、显式工具 allowlist、授权 scope、成本/调用预算、幂等键、结果大小上限、协作截止时间、失败类型和审计记录；`app/agents/tooling.py` 提供受限 `review_one_submission` skill，仅可按当前正式蓝图调用单条程序规则或语义规则；`app/services/checks.py` 将它接入真实审核执行路径。模型不会自行决定工具名称、SQL、文件路径、授权主体、规则 ID 或网络目的地。每次调用在审计事件里附当前主体、检查运行、规则 ID、工具类型、结果状态及耗时；复核 Findings 只向该任务的授权组织者展示当前运行轨迹，界面可展开查看逐步运行记录。

**需求起草的长调用恢复**：`app/services/agent_requests.py` 将起草/修订先落库再执行，按任务顺序串行处理，使用任务+账号+请求 ID 唯一键与 payload 哈希防止断线重放；请求状态可由所有者读取，API 响应丢失时前端先查状态，再按同一请求编号幂等补投。页面将请求 ID 与当前输入暂存在原有 owner/task sessionStorage 中，重载后恢复用户原文、显示队列/运行状态并继续查进度。超时/无效模型回应不会生成新版本；旧草案保留，允许用同一请求编号重试。新草案/并发修订的基线不再最新时 fail closed，要求刷新，避免旧结果覆盖新版本。Worker 按配置的模型最长调用预算设置宽裕租约并恢复超期 running job；attempt fence 阻止迟到的旧 Worker 提交结果。

此请求队列是 SQLite/单 API 单 Worker 的本地应用机制，不是分布式任务系统；部署多副本前仍需共享数据库上的行锁/租约设计、死信管理、退避和监控。后台任务与 Worker 可同时尝试同一任务请求，但一次只处理该任务头部队列请求。

安全边界和限制：参数/结果验证失败、越权、预算耗尽、超时、运行异常一律 fail closed 为 `failed`，由现有审核状态交给人工或重试；审计只记录工具名、执行者账户范围、主体/运行/规则 ID、状态、耗时、模拟标记及幂等键哈希，不保存原始材料、参数或结果。授权 Findings API 仅为组织者读取当前检查运行的过滤后轨迹；旧运行的轨迹不混进新版本。幂等回放缓存是单次 harness 生命周期内存态，未承诺跨进程 exactly-once。skill 对失败停止策略与需人工处理项留痕有显式控制。截止时间通过 context 传给工具协作执行；Python 无法强制杀死忽略 deadline 的 handler，新增 handler 必须把剩余时限传入阻塞 I/O，且不得启用脱离请求的副作用。此实现是本地应用内部的受控 skill/harness，不是 MCP Server、不是通用规划 Agent，也没有给 Agent 增加外部网络工具。

自动化回归覆盖授权、schema 注入拒绝、预算、幂等与权限重放、结果上限、异常隔离、skill 工具/步数上限、失败停止策略、unknown/failed 的人工接手标记和审计脱敏；本轮完整单元测试及演示库回归通过，后续再考虑：

1. 为工具轨迹补充更细的版本/延迟/重试关联及长期幂等恢复策略，评估 worker crash/重复投递边界。
2. 用授权脱敏材料和对抗性提示注入样本验证 skill 的引用定位、资源上限、人工转交与用户可理解度；不从种子样本宣称准确率。
3. 暂缓需求设计 Agent 的 tool 化，直到定义完整草案/澄清幂等恢复合同；不让通用工具调用绕开现有发布校验。
4. **MCP adapter 当前没有必要**：核心流程的工具由单体应用内服务提供，也没有跨应用/跨组织工具需求；未来出现明确互操作用户故事时，再在同一 scope、审计与预算边界上暴露受限 adapter。
5. 任何后续工具先由离线假 handler 和攻击测试验收；MCP 不替代授权、隐私、发布或人工验收决策。

## P2：韧性、可达性和评估

- 逐页键盘/读屏检查：焦点恢复、错误摘要、弹窗关闭、状态播报频率；320/390/768px、长任务名/文件名、200%缩放、低网速/断网不遮挡关键操作。
- 三类草稿明确本地/服务器/正式版本边界，考虑主动保存复核草稿到服务器的独立产品需求；未经确认不把敏感未提交意见跨设备同步。
- 授权样本评估：可定位引用、问题漏报/误报、不可读区域、注入、预算耗尽；按规则/文件类型分组，记录人工修正成本。先定义阈值再评估，不从演示种子推导准确率。
- 清理依赖弃用和外键环警告，锁定可重复依赖、CI回归与备份恢复演练；多 Worker 前先建立领取锁/租约，不能直接多进程重复执行。
