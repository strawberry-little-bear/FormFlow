[Heading 1] 1 产品定位与使用场景
[Normal] 收齐啦以一个“收集任务”为最小单元，把组织者提出的要求转成可执行蓝图，让个人或团队按要求提交材料，通过证据化反馈完成补正，最后交付可核对的文件包与汇总表。它不是通用工作流引擎，也不以聊天本身作为主要交互。
[Heading 2] 需要解决的问题
[Normal] •  要求分散在通知、表格和群消息中，提交者不容易判断到底交什么、什么时候算交完。
[Normal] •  组织者反复下载、打开和核对材料，缺交、错期次、附件遗漏与资格核实混在一起。
[Normal] •  同名文件和多轮补交容易覆盖，验收与最终打包可能引用不同版本。
[Normal] •  反馈只有“材料不合格”而没有位置与改法，造成反复沟通。
[Heading 2] 两类首批场景
[Heading 2] 预期价值与验证方式
[Normal] 预期价值是让要求可执行、补正可操作、结果可按正确版本交付。是否减少工作量，要用同批材料的人工流程对照验证，记录处理时间、打开文件次数、补交轮数以及纠正机器意见的成本；目前不承诺准确率或省时比例。
[Heading 2] 明确不做的判断
[Normal] 不自动评价思想、文笔或作品优劣，不认定出勤、学籍和资格真实性，不判断签名效力，不把相似或同名线索直接认定为抄袭、造假或重复报名，也不做 AI 写作检测。
[Normal] 建议先用团课完成一条纵向闭环，再用比赛证明内核复用；这仍是待确认的实施顺序，而不是同时开发两个独立产品。
[Heading 1] 2 首版范围与角色权限
[Heading 2] 一个内核与两个独立维度
[Normal] 名单制与开放制决定是否存在应交分母；个人与团队决定提交主体和字段结构。两组维度可以组合，共用草稿、正式版本、检查、人工决定和导出内核。
[Heading 2] 身份与访问提案
[Normal] 组织者使用账号；提交者使用绑定稳定主体 ID 的可撤销持有凭证。凭证不是实名认证，姓名、学号、队名都不能作为读写权限密钥。名单制私下发放邀请；开放制先展示公共介绍，再创建私有提交空间。
[Normal] 访问找回由组织者核验后重发凭证并撤销旧凭证，不提供公开姓名检索。任务公共链接不能访问任何报名记录。联系人转移若后续实现，必须明确撤销旧权限。
[Heading 2] 核心候选 P0
[Normal] 任务起草与发布预览；简单条件规则；名单与开放提交；私有上传和正式回执；不可变版本；后台基础检查与有限语义检查；证据化补正、申诉和人工验收；站内结果、催交名单与复制文案；快照 CSV 与 ZIP；关闭与归档。实现阶段还需完成持久化、权限、恢复和公网安全。
[Heading 2] 不混入首版
[Normal] 真实外发通知、增量审核、多人协作、成员逐人确认、复杂规则迁移、多阶段活动、名额候补及本地助手不作为核心 P0 的前提。每任务先只支持单一阶段，不支持任意嵌套规则。
[Heading 1] 3 任务蓝图与发布确认
[Normal] 任务蓝图是同一任务的结构化规则来源。自然语言对话和手动编辑共同修改一份草案，用户不需要理解代码；页面说明、检查逻辑、截止政策和导出要求不得各自维护一套。
[Heading 2] 规则能力必须可见
[Normal] 规则分为确定性检查、语义检查、跨材料一致性和仅人工项。界面显示“已支持”“需人工”或“需澄清”，不能把无法执行的要求包装成自动能力。每项规则保留原始要求与澄清来源，不暗加字数、签章、签到或其他组织者未提出的门槛。
[Heading 2] 发布前校验
[Normal] •  仅支持可解释的简单枚举条件；预览每个分支，防止隐藏字段仍强制必填。
[Normal] •  验证引用存在、日期顺序、重复与冲突字段、依赖环及删除字段造成的影响。字段改名不改变 ID。
[Normal] •  关键歧义或非法配置阻止发布；已确认的人工项可以发布，但不能继续标为自动检查。
[Normal] •  发布摘要逐项确认对象、材料、检查能力、双截止、验收、交付、用途、模型处理与留存，不能以“一键已读”代替答案。
[Normal] 发布时固定蓝图版本并校验草稿版本。实质规则变更需明确新版本及受影响范围，不得静默改写已经发布的提交义务；复杂迁移策略留待后续设计。
[Heading 1] 4 两个 Agent 与程序边界
[Normal] 首版仅保留需求 Agent 和审核 Agent。Agent 负责理解、调查和解释，程序负责身份、事实与状态。能确定性计算的规则不交给模型反复判断，也不为了展示 Agent 数量拆分多余角色。
[Heading 2] 需求 Agent
[Heading 2] 审核 Agent
[Heading 2] 工具与停止条件
[Normal] 工具权限由程序限定到当前授权任务与快照。上传文件中的“忽略规则”“访问他人材料”等文字只作为待分析数据，不能成为系统指令。模型结果必须经过结构与引用校验。
[Normal] 每次审核需有页数、OCR、调用、重试与费用预算；证据不足、工具失败或预算耗尽时明确记录未完成项并转人工，不能虚构全通过。具体模型、解析器、供应商与限额尚未决定。
[Heading 2] 程序保留的权力
[Normal] 发布与提交事务、权限、服务端时间、唯一性、计数、幂等、版本指针、状态转换、通知、快照与打包由业务代码决定。自然语言批量指令也必须转换为可预览、可授权、可追踪的具体操作。
[Heading 1] 5 完整业务工作流
[Normal] 主流程：澄清要求 → 确认蓝图 → 发布 → 私有登记与上传 → 正式收件 → 检查 → 补正或复核 → 验收 → 固定交付 → 关闭归档。
[Heading 2] 三条不能混淆的事实
[Normal] •  上传成功不等于正式提交；正式提交成功不等于检查通过。
[Normal] •  规则检查通过不等于资格符合，也不等于材料已验收。
[Normal] •  当前版本验收不代表全体收齐；部分正式包必须披露排除与缺交。
[Normal] 组织者在工作台管理主体和待办；提交者在私有空间查看回执、版本和补正。两端共享同一任务规则与事实，不依赖聊天记录作为唯一业务凭据。
[Heading 1] 6 时间政策与异常分支
[Heading 2] 首次截止与补正截止分离
[Normal] 以服务端成功记录正式提交的时刻为收件时间，不以开始上传、点击按钮或模型完成时间计。任务显示明确时区；存储使用统一时刻或带偏移时间。初次接收区间为 [开放时刻, 首次截止)，恰等于截止时刻不接收首次提交，界面须提前说明。
[Normal] 只有已形成正式提交的主体才能使用补正窗口。首次截止前仅有草稿或上传者，不能在截止后借“补正”完成首次报名。组织者批准个别迟交时，记录对象、批准者、理由和有效新期限，保留原截止及历史事实。
[Heading 2] 故障不应改变公平性
[Normal] 按时成功收件后模型排队或失败，不算迟交；服务异常不能让回执消失。后台失败、人工等待、材料问题应分别展示，避免把系统失败转嫁为提交者不合格。
[Heading 1] 7 状态分层与统计口径
[Normal] 不设置一个囊括所有事实的万能状态。任务生命周期、收件事实、文件状态、检查运行、规则结果、材料验收、资格和名单例外分别记录，页面再计算主摘要与可重叠待办。
[Heading 2] 当前检查摘要
[Normal] 先核对适用规则覆盖与当前运行。主摘要优先显示：未解决阻塞 → 待补正；否则有 unknown 或人工项 → 待人工；否则失败或缺结果且无可执行作业 → 检查未完成；否则有有效作业 → 待检、检查中或重试；全部适用项满足、不适用或已被有效人工处置 → 规则通过。
[Normal] 主摘要不抹去其他待办。同一主体可同时“待补正”“待人工”“检查未完成”；运行中已发现问题，也应保留检查仍在继续的标记。资格、免交和验收单独展示。
[Heading 2] 名单制计数
[Normal] 当前名册 = 当前应交 + 有效免交；当前应交 = 已正式提交 + 未正式提交。验收、补正和人工待办都是已提交的子集，不能相加成总人数。名册移出、撤回和免交变更保留历史，分母变化需要说明。
[Heading 2] 开放制计数
[Normal] 只统计登记主体、正式报名、当前验收及待办。草稿登记不是正式报名，撤回单列。没有名册就不显示缺交、未报名人数或完成率；团队数和成员人数必须使用不同单位。
[Heading 1] 8 版本幂等与并发保护
[Heading 2] 七条业务不变量
[Normal] •  一次正式提交固定字段值和文件引用；草稿与上传不构成收件。
[Normal] •  历史收件事实不会因模型失败、撤回或后续拒收被抹除。
[Normal] •  一个主体只有一个当前正式版本指针；新草稿不抢占它。
[Normal] •  检查、人工决定与验收绑定作用域，不无条件继承。
[Normal] •  当前摘要仅接受当前版本、有效运行和兼容配置的结果。
[Normal] •  生成包读取固定快照，而非生成期间变化的最新文件。
[Normal] •  所有原件、证据、索引、预览与包均由程序校验访问权。
[Heading 2] 正式提交的幂等设计
[Normal] 提交意图绑定操作者、任务、主体、幂等键、内容摘要及预期当前版本。同键同内容返回同一回执；同键异内容报冲突。权限、时间、文件就绪等验证通过后，在可靠提交边界同时记录正式版本和检查意图，投递失败可以恢复。
[Normal] 超时重试先查原键是否已经成功，不立即重新报名。已经成功的请求跨过截止后仍可取回原回执，这不是再次提交，不应重新判为迟交。
[Heading 2] 首版取舍
[Normal] 相同文件名不代表相同文件，以稳定文件 ID 和版本区分。部分补交先完整复核，待正确性得到验证后再实现缓存复用与依赖失效。
[Heading 1] 9 证据对象与结论强度
[Normal] 每条规则结果应能回答：依据哪个要求，检查哪个版本，实际看到了什么，哪些范围没有读到，结论会阻塞什么，提交者下一步怎么做。引用存在不等于理解正确。
[Heading 2] 三类证据与结论边界
[Heading 2] 缺失判断的最低要求
[Normal] 必交附件以快照槽位和条件结果确定，明确字段按字段值与必填条件确定，不需要模型证明。固定模板要说明模板版本及区域已完整可辨；自由文档必须说明覆盖范围、未读与失败页和候选表达。
[Normal] 只要关键范围未覆盖、区域不可读或等价表达存疑，就输出 unknown。完整覆盖只是必要条件，不是语义正确的保证；首版自由语义的“缺失”仍默认人工确认，不自动拒收。
[Heading 2] 补正反馈范例
[Normal] C-R03 要求报告为“2026 秋季第 1 期”；当前登记为第 1 期，报告第 1 页标题写第 2 期。建议替换正确期次报告，或申请人工复核。该问题阻塞本版本材料验收，不构成资格处罚。不得附加蓝图之外的字数或签名要求。
[Heading 1] 10 人工复核与申诉
[Normal] 人工复核不是绕过规则的万能通过按钮。组织者先查看具体规则、当前版本、证据与提交者解释，再明确决定范围和理由；原始机器意见与历史操作均保留。
[Heading 2] 决定记录
[Normal] 至少包括操作者、时间、理由、任务、主体、提交版本、规则或资格作用域、预期当前版本，以及可选失效时间。默认不扩大到未来版本；旧文件例外不自动适用于后来替换的文件。
[Heading 2] 验收前检查
[Normal] •  确认所见仍是当前快照，当前操作者拥有相应权限。
[Normal] •  没有未解决阻塞；unknown、失败、人工项和未完检查均有明确处置。
[Normal] •  若启用资格前提，应已明确符合；资格不能被材料通过自动推导。
[Normal] •  验收必须单独确认依据，不能通过一次点击静默豁免全部未知项。
[Heading 2] 提交者的申诉路径
[Normal] 提交者可查看问题、引用位置和建议改法，选择补交或解释。组织者可以核对原文、纠正误报或批准有范围的例外。反馈应说明剩余待办：例如姓名已核实，不代表错期次问题同时解除。
[Heading 2] 交互保护
[Normal] 理由为空时不允许产生决定；历史页面只读，不误操作当前版本。提交时服务端再次校验版本，若期间已有补交，应提示冲突并重新核对。撤销后重新计算状态，不能继续沿用失效的验收资格。
[Heading 1] 11 交付快照与导出
[Normal] 交付目标不是“下载最新文件”，而是生成一份能解释纳入、排除和版本来源的固定结果。汇总 CSV 和材料 ZIP 必须引用同一个快照，避免表格与文件错位。
[Heading 2] 正式与整理预览
[Heading 2] 生成流程
[Normal] •  选择范围、导出字段、分组与命名；预览每个主体纳入或排除的原因。
[Normal] •  固定蓝图版本、主体与正式版本、文件集合、人工决定引用、字段和命名策略。
[Normal] •  记录清单、大小和必要校验信息；同一导出作业重试仍读取同一快照。
[Normal] •  生成期间有新提交只提示“有更新”，用户可另建快照，原包不静默改变。
[Normal] •  下载时继续校验权限，输出操作和失败原因可追踪。
[Heading 2] 命名与完整性
[Normal] 目录和文件名包含稳定 ID 以避免同名覆盖；保留原始名称映射，原件不改写。处理路径穿越、重复名、非法路径与 CSV 公式前缀，不能让用户提供的名称成为任意文件路径或可执行公式。
[Heading 2] 历史版本与撤权
[Normal] v1 已验收而 v2 仅为草稿时，当前仍是 v1；重开后正式提交 v2，则新包默认排除该主体直至 v2 重新验收，不回退引用历史 v1。历史包的内容清单保持不变。
[Normal] 快照固定的是内容选择，不是永久下载承诺。安全删除、授权撤销或资料撤回可能使旧包不可再下载；访问控制优先于历史包可用性，应显示原因而不是无限重试。
[Heading 1] 12 页面与交互设计
[Normal] 页面设计围绕组织者的待办和提交者的行动，而不是以大聊天框占据主界面。桌面便于批量管理，提交页移动优先；低保真原型只验证信息层级、状态与操作，不锁定颜色、布局和品牌。
[Heading 2] P01 任务设计台
[Normal] 提供一句话起草、模板和手动配置三种入口。对话与结构化编辑更新同一草案，显示修改影响。首屏包含原始要求、少量高影响澄清、字段材料、来源与能力标签、条件分支预览及发布摘要。
[Normal] •  已知信息不重复追问；低影响默认建议在发布前说明来源。
[Normal] •  字段改名保持 ID；删除被引用字段先列出规则、条件和导出依赖。
[Normal] •  草稿冲突保留本地内容并展示差异；空输入不生成虚构要求。
[Normal] •  发布校验对象、材料、能力、双截止、验收、交付及数据用途；关键冲突定位到具体项。
[Heading 2] P02 任务工作台
[Normal] 首屏回答“谁没交、谁要改、谁等我决定”。一行一个主体，不一行一个文件。显示当前正式版本、材料检查、资格、验收和下一步；有历史验收时显示“当前 v2，历史 v1 已验收”，不能只有一个绿色勾。
[Heading 2] 整体导航
[Normal] 任务列表与公共介绍连接设计台、工作台、提交空间、证据复核和交付预览；找回、通知、关闭归档需有明确入口。公共介绍不暴露他人姓名、材料或报名详情。
[Heading 1] 12 页面与交互设计续
[Heading 2] P03 证据复核
[Normal] 以规则待办列表配合证据区域：展示要求来源、文件版本、原文或图像、登记字段对照、提取方法和覆盖缺口。选择规则即切换对应位置，支持确认问题、纠正误报、批准例外、要求补正和当前版本验收。
[Normal] 证据找不到时不继续基于该证据自动阻塞，转人工。未知、失败和未处置问题要明确列出；历史版本只读，操作时验证当前 revision。权限过期后停止加载原文，不借缓存继续展示未授权资料。
[Heading 2] P04 提交与补正
[Normal] 移动优先展示任务与组织者、明确双截止、本人或本队身份、结构化字段和材料槽位。草稿文件与正式文件分开标记，上传阶段、失败原因和重试动作清楚可见。“保存草稿”与“正式提交并检查”是不同操作。
[Normal] •  正式提交成功展示稳定回执、服务端时间和版本，可在超时后恢复。
[Normal] •  补正显示哪里有问题、怎么改、引用证据、剩余待办和申请复核入口。
[Normal] •  部分替换可保留未改文件，但最终提交固定完整快照，并提示重检与重新验收影响。
[Normal] •  不把上传进度、模型进度和验收状态合成一个虚假的完成百分比。
[Heading 2] P05 交付预览
[Normal] 先选择正式或整理预览，再选择范围、字段、目录与命名。逐行展示纳入版本、排除原因及存在未提交修改的提示。确认后固定快照，显示生成阶段、失败重试和之后有新提交的提醒。
[Heading 2] 跨页面体验要求
[Normal] 现有原型冒烟检查不代表完整无障碍审计、跨浏览器兼容性验证或真实用户可用性研究。视觉样式将在后续设计中单独确认。
[Heading 1] 13 团课报告样例
[Normal] 样例编号 BP-C-001。以下全部为虚构配置，样例内的澄清与确认仅用于演示，不代表真实组织者批准。
[Heading 2] 要求与澄清
[Normal] 收名单内同学的“2026 秋季第 1 期”团课报告，包含本人姓名、期次、活动内容和个人收获，按班级整理。接受一份 PDF 或 DOCX，最大 10 MiB、20 页，组织者最终人工验收。不加字数、签到、签名、思想评价或 AI 写作判断。
[Normal] 任务时区 Asia/Shanghai。2026 年 11 月 1 日开放；须在 11 月 8 日 18:00 前完成首次正式提交；已有正式提交者可在 11 月 10 日 18:00 前补正。这是演示日期，不是开发工期。
[Heading 2] 初始虚构状态
[Normal] 计数核对：名册 5 − 免交 1 = 应交 4；正式 3 + 未正式 1 = 应交 4；当前验收 1。待补正 1、待人工 1 和检查未完成 1 不是互斥分组，不能相加成已提交总数。
[Normal] 建议演示顺序：澄清规则 → 发现错期次与模糊姓名 → 只纠正姓名而保留期次阻塞 → 有范围的例外或补正 → 人工终验 → 固定包 → 之后提交不改变原包。
[Heading 1] 14 比赛报名样例
[Normal] 样例编号 BP-T-001。开放团队报名，2–5 人，分数字与实物赛道；登记队名、项目名、成员、联系人、邮箱和联系人代填声明。联系人须为成员，经澄清设定每人只参加一队；同名只能作为人工核实线索。
[Normal] 简介一份 PDF 或 DOCX，最大 10 MiB、20 页。实物赛道另需 1–3 张 JPG 或 PNG，每张最大 10 MiB；数字赛道不要求照片。邮箱默认不导出，资格由人工独立核实，符合资格是验收前提。
[Normal] 演示任务须在 2026 年 11 月 12 日 18:00 前首次提交，已有正式版本者可在 11 月 14 日 18:00 前补正，时区为 Asia/Shanghai；日期和要求均不是实际活动承诺。
[Heading 2] 初始虚构状态
[Normal] 计数核对：登记 4 队、成员 11 人、正式报名 3 队、当前验收 1 队、资格待核 2 队。开放制不存在应交分母，不显示缺交或完成率。
[Heading 2] 复用内核而非新增产品
[Normal] 比赛复用蓝图、私有空间、不可变版本、证据复核和快照交付；变化集中在字段、条件附件、团队关系与独立资格。补齐照片不自动使资格符合，资格符合也不自动验收材料。
[Heading 1] 15 工程架构与可靠性
[Normal] 架构建议为 Web 前端、业务 API、关系数据、私有对象存储、独立异步 Worker、文档解析与 OCR、模型网关及审计恢复。此处说明职责，不锁定语言、框架、数据库产品或模型供应商。
[Heading 2] 逻辑实体
[Normal] 账号与访问授权；收集任务与蓝图版本；主体、成员、名册与免交；提交与正式 Revision；文件与解析索引；检查 Run、规则结果、问题与证据；人工决定；交付快照与作业；通知意图与实际发送；审计事件。物理表可合并，但不能把这些语义只存进不可验证的聊天记录。
[Heading 2] 一致性与恢复
[Normal] •  正式版本与检查意图可靠记录，避免数据库成功但队列任务丢失。
[Normal] •  重试不重复建报名、验收或通知；当前比较与写回使用事务或等价并发控制。
[Normal] •  清理孤儿上传，但不提前删除仍被历史与有效快照引用的文件；删除义务另行处理。
[Normal] •  模型不可用时收件仍可用；阶段进度真实，不伪造完成比例。
[Heading 2] 部署验证顺序
[Normal] 先验证持久化、健康检查与迁移，再跑通真实私有上传、下载与后台任务，之后接模型与解析，完成补交与打包。上线前验证 HTTPS、密钥、日志、资源限制、备份和实际恢复，并在另一设备及服务重启后复查。单服务器仅是起点，不是安全、容量或高可用保证。
[Heading 1] 16 安全与数据治理
[Normal] 收集材料可能包含个人资料。首版必须围绕必要字段和最小授权设计；不能因为是课程作品，就默认真实资料可以公开、长期保存或用于模型训练。
[Heading 2] 访问与授权
[Normal] •  任务、主体与凭证隔离；稳定 ID 不能替代授权校验。
[Normal] •  原文件、裁切、预览、证据、解析索引及导出包全部校验权限，短期下载链接也需遵守撤权策略。
[Normal] •  凭证可撤销、可过期；找回不通过公开姓名查询。私有 API 不依赖前端隐藏按钮保障安全。
[Heading 2] 文件与导出安全
[Normal] 核验真实类型，不只信任扩展名；限制数量、大小、页数、压缩资源和解析时间；在隔离环境解析，不执行宏、脚本或上传代码。路径、重名、非法名称和符号链接风险在生成与同步环节分别防护。CSV 字段防公式注入，保留安全名称与原名映射。
[Heading 2] 模型输入与提示注入
[Normal] 只提供完成规则所需的当前授权数据，限制页数、调用与工具范围。文件内容不提升为指令；模型无权扩大访问、改规则或终验。结构化输出由程序校验，引用是否支持语义结论仍需人工答案评估和申诉。
[Heading 2] 用途 留存与删除
[Normal] 实现前应确定实际部署和数据处理责任。本文提出产品与工程控制要求，不构成已经完成安全审计或法律合规认证的声明。

[Heading 1] 19 可选本地同步扩展
[Normal] 本地助手可让组织者把交付材料保存到指定目录，减少重复下载整理；但设备授权、离线副本、冲突和删除不是普通 ZIP 下载能够替代的。该能力作为独立探索，不阻塞核心 Web P0，目前未实现，也未指定桌面框架。
[Heading 2] 最小候选范围

[Normal] •  先同步指定正式快照，优先运行一次；后台周期与提醒须由用户明确开启。
[Normal] •  显示任务、快照、阶段、最后成功时间、部分失败与授权状态。
[Heading 2] 目录与完整性
[Normal] 专用根目录下按稳定任务 ID 分组，再以 snapshot_001、snapshot_002 保存固定快照。latest.json 仅在全部校验成功后更新。清单包含对象 ID、版本、安全相对路径、大小和内容校验值；新快照新建目录，不就地改旧包。
[Normal] 拒绝绝对路径、上级跳转、符号链接逃逸、保留名和大小写折叠冲突。临时写入并校验后再原子替换；远端清单不赋予任意本地文件权限。凭证不得写入清单或日志，具体安全存储待平台确认。
