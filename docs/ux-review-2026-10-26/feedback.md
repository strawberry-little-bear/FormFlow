# 验证档案：启动参数、失败状态与责任分工

这份公开档案展示四个入口场景中的可见结果：启动器如何使用自定义端口，异常路由如何结束加载，提交者如何区分自己的补正事项与组织者待办。运行使用虚构演示数据并留空模型密钥，截图、脚本和环境记录保存在本目录。

## 场景与结果

| 场景 | 页面结果 | 接下来由谁处理 |
| --- | --- | --- |
| 使用 `--reset --port 8011` 启动 | 启动器检查并使用传入端口；只有该端口确实被占用时才提示冲突，并显示实际端口号 | 启动者选择可用端口后重试 |
| 打开 `#/roster/9999` | 加载占位被替换为任务不存在的说明，并提供返回工作台入口 | 组织者选择有效任务 |
| 打开 `#/review/1/9999` | 页面显示主体不存在的失败状态，不再遗留“正在读取检查结果…” | 组织者选择有效提交者或返回工作台 |
| 提交者查看已提交材料 | 可由提交者处理的缺项，与组织者核对、检查未完成和等待验收分开显示 | 提交者处理自己的事项，组织者完成确认 |

## 读者可以核对什么

这些场景共同验证了一个产品约定：失败状态要说明原因和恢复入口；无效编号不能让页面永久停在加载中；检查未完成不能被包装成提交者的不合格；组织者需要核对的内容也不会被写成提交者的待办。

## 复现边界

结论只适用于指定版本、虚构数据和本地浏览器。它验证的是页面状态和恢复路径，不代表真实 provider 的模型质量、敏感材料处理、生产并发或公网部署安全。
