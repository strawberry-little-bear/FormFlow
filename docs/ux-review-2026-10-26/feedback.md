# 验证档案：启动参数、失败状态与责任分工

这份档案展示 FormFlow 面对四个常见入口问题时，页面如何说明发生了什么，以及下一步应该由谁完成。数据为虚构演示数据，模型密钥留空；对应截图、脚本和运行条件保存在本目录。

## 用户场景

| 场景 | 页面结果 | 下一步 |
| --- | --- | --- |
| 使用 `--reset --port 8011` 启动 | 启动器检查传入端口；只有端口确实被占用时才提示冲突，并显示实际端口号 | 启动者选择可用端口后重试 |
| 打开 `#/roster/9999` | 加载占位被替换为任务不存在的失败状态，并提供返回工作台入口 | 组织者选择有效任务 |
| 打开 `#/review/1/9999` | 页面显示主体不存在的失败状态，不再遗留“正在读取检查结果…” | 组织者选择有效提交者或返回工作台 |
| 提交者查看已提交材料 | 可由提交者处理的缺项与组织者核对、检查未完成和等待验收分开显示 | 提交者处理自己的事项，组织者完成确认 |

## 对产品的意义

失败状态同时说明原因、影响和恢复入口。无效编号不会让页面永久停在加载中；模型未完成不会被写成提交者的待办；组织者需要核对的事项也不会被误导成提交者可以解决的问题。

## 复现边界

结论只适用于指定版本、虚构数据和本地浏览器。它验证的是页面状态和恢复路径，不代表真实 provider 的模型质量、敏感材料处理、生产并发或公网部署安全。
