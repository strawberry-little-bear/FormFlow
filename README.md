# FormFlow · 收齐啦

### 从通知到验收，把材料收集变成一条可追溯的流程

FormFlow 是面向报名、征集、材料验收和归档的 AI 工作流。组织者提供通知、名单和模板，系统整理出可确认的收集规则；提交者按清单填写和上传；审核 Agent 再把跨文件核验结果连同证据位置交回组织者处理。

## 作品解决什么问题

| 组织者 | 提交者 |
| --- | --- |
| 上传通知、名单、模板和补充说明 | 使用一次性凭证进入任务 |
| 查看需求 Agent 生成的字段、材料槽位和规则 | 填写身份信息、上传多份材料、保存草稿 |
| 确认冲突和澄清问题后发布任务 | 正式提交并查看回执、补正入口 |
| 按规则查看证据、处理人工确认、导出交付包 | 只处理明确属于自己的补正事项 |

一次提交会被拆成可解释的检查项：`satisfied` 表示已有证据支持规则，`issue` 表示发现需要处理的问题，`unknown` 表示证据不足，`failed` 表示检查没有完成。上传文件不等于正式提交，检查未完成也不会被包装成“不合格”。

## 一条完整的材料链路

1. **整理要求**：组织者把通知、名单和模板交给需求 Agent，得到带来源引用的字段、材料槽位和审核规则草案。
2. **确认发布**：组织者处理冲突和澄清问题，确认蓝图后发布收集任务。
3. **提交与核验**：提交者填写身份信息、上传多份材料并正式提交；审核 Agent 按规则逐条比对跨文件信息，返回结论和证据位置。
4. **人工接管与交付**：组织者核对原文、处理补正和人工项，最后生成 CSV 与 ZIP 快照。

这条链路把“要求是什么”“材料是否满足”和“谁需要下一步行动”放在同一条可追溯路径里。作品首页先展示整体路线，组织者可以继续查看证据和交付快照，提交者则能完成提交、查看回执并处理明确属于自己的补正事项。

## 两个 Agent，一条责任链

**需求 Agent** 把通知、名单和模板变成规则草案。它识别适用人员、身份字段、材料、格式、数量、命名、页数、时间和跨材料检查项；资料冲突或要求含糊时保留来源并提出澄清问题。蓝图必须经过组织者确认，才会成为正式任务规则。

**审核 Agent** 按正式规则检查一次提交。它可以核对姓名、学号等身份信息，检查文件属性、内容覆盖和跨文件一致性，并把每条判断定位到相关材料。证据是可追溯的定位线索，组织者仍可打开原文完成最终判断。

## Agent 如何被约束

- **Skill** 固化资料提取、规则编译、证据引用和结构化输出的方法。
- **Harness** 限制任务范围、工具白名单、预算、超时、重试和人工接管。
- **MCP** 提供受限的只读任务状态和运行摘要，不读取逐人材料正文，也不提供写入工具。
- **确定性检查** 负责文件类型、数量、大小、时间、版本和导出条件；模型负责理解、比对和解释；组织者负责最终验收。

材料审核优先使用部署者配置的 provider 的 PDF 或图片输入。provider 不支持、文件超限或调用失败时，才进入文字解析或 OCR 降级；`direct` 模式会明确报告失败，不会偷偷切换。模型返回的文件和页码是定位线索，组织者仍需核对原文。

## 立即体验

演示数据、人物、文件和审核轨迹都是虚构的，不需要模型密钥：

```bash
git clone https://github.com/strawberry-little-bear/FormFlow.git
cd FormFlow
python scripts/start_demo.py --reset
```

打开终端显示的地址，使用演示账号：

```text
账号：demo
密码：demo1234
```

进入后先看组织者的“需求设计 → 收集工作台 → 证据复核 → 交付与归档”，再用提交者入口完成“填写 → 上传 → 正式提交 → 查看回执”。完整操作顺序和复现脚本见[体验指南](docs/demo-guide.md)。

## 接入自己的模型

部署者可以在本机 `.env`、进程环境或部署平台 Secret 中配置 provider、模型名和 API Key。FormFlow 不把 API Key 写入数据库、浏览器响应、日志、审计事件或 MCP 配置；材料是否发送给外部 provider，以及 provider 如何留存和处理材料，由部署者自行决定。配置示例和输入模式见[部署与模型接入](docs/deployment.md)。
