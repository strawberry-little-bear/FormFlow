# FormFlow · 收齐啦

### 把分散的通知，变成一条可追溯的材料流程

FormFlow 面向报名、征集和评审场景。组织者把通知、名单、模板和补充说明交给系统，需求 Agent 将它们整理成可确认的收集任务；提交者在线填写并提交材料；审核 Agent 再按规则逐项核对多份文件，给出结论、证据位置和下一步动作。

打开演示后，先从任务和进度开始，再沿着组织者、提交者两条路径走到证据复核和交付归档。想了解实现方式，可以在运行过程中查看 Agent、Skill、Harness 与 MCP 的职责边界。

## 它解决什么问题

一条通知往往同时包含人员范围、字段要求、附件格式、截止时间和审核标准。实际执行时，这些信息分散在通知、名单、模板和聊天记录里；提交后，又要在表单和多份附件之间反复找姓名、学号、格式和正文内容。

FormFlow 把“收集要求”和“核验材料”放进同一条可追溯流程：

1. 组织者导入通知、名单、模板和其他参考资料。
2. 需求 Agent 提取字段、材料槽位、时间策略和审核规则，并保留来源与冲突。
3. 组织者编辑并确认蓝图，确认后才发布任务。
4. 提交者填写信息、上传材料、保存草稿并正式提交。
5. 审核 Agent 按已发布规则逐项检查，展示结论、证据和责任归属。
6. 组织者处理人工确认，生成可交付的 CSV 与 ZIP 快照。

## 两个 Agent，分工清楚

### 需求 Agent：从资料到收集蓝图

需求 Agent 读取组织者提供的通知、名单、模板和补充说明，整理出适用对象、身份字段、材料要求、截止时间和跨材料核验规则。每项要求都保留来源资料和定位；资料之间有冲突或描述不清时，系统先提出澄清问题，不把猜测直接变成正式规则。

组织者可以在发布前编辑字段、材料槽位和规则。蓝图需要明确确认后才会成为任务约束。

### 审核 Agent：从提交材料到有证据的结论

审核 Agent 同时查看表单字段、名单和多份材料，核对身份是否一致、文件属性是否符合要求、正文是否覆盖规则，以及文件之间是否存在矛盾。每条检查都返回以下四种状态之一：

- `satisfied`：已有证据支持要求；
- `issue`：发现需要处理的问题；
- `unknown`：证据不足，需要人工判断；
- `failed`：检查过程没有完成。

结果会带上文件、页码、区域和引用片段。模型给出的页码或区域是定位线索，程序会检查引用格式和文件范围，但最终仍由组织者打开原文完成确认。

## AI、程序检查和人工确认如何协作

文件审核优先使用部署者选择的模型的 PDF 或图片输入能力。provider 不支持文件输入、文件超限或调用失败时，系统才进入文字解析或 OCR 降级；未读页面会被保留为覆盖缺口，不会被当成通过。

文件扩展名、大小、数量、页数、字段格式、截止时间和导出条件由程序检查。模型负责理解、比对和解释。Skill 固化 Agent 的步骤和输出格式，Harness 限制任务范围、工具、预算、超时、重试和人工接管，MCP 只提供受限的只读运行上下文。

FormFlow 不托管模型密钥。API Key 只由部署者保存在本机 `.env`、进程环境或部署平台 Secret 中，不写入数据库、浏览器响应、日志、审计事件或 MCP。启用真实 provider 后，材料是否发送到外部服务由部署者自行决定。

## 三分钟体验

演示数据、人物和材料均为虚构。留空模型密钥也能体验组织者和提交者的完整路径，包括草稿、正式提交、失败恢复、人工接管和交付归档。

```bash
git clone https://github.com/strawberry-little-bear/FormFlow.git
cd FormFlow
python scripts/start_demo.py --reset
```

打开启动器显示的地址，使用演示账号：

```text
账号：demo
密码：demo1234
```

推荐体验顺序是“需求设计 → 收集工作台 → 提交者端 → 证据复核 → 交付与归档”。每一步都保留任务上下文，按页面上的下一步入口即可完成一条闭环；具体操作见[体验指南](docs/demo-guide.md)。
